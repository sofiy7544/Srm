**КРИТИЧЕСКИЕ ДЫРЫ — ИСПРАВЛЕНО СЕЙЧАС**


**1. ⚠️ Утечка данных через `/activities/client/:id` и `/activities/lead/:id`**

Любой риелтор мог открыть активность ЛЮБОГО клиента в системе — endpoint не проверял доступ.

→ Исправлено: `activities.controller.ts` теперь подгружает клиента/лида, проверяет `assignedUserId` через `getAccessibleUserIds()`. Чужие активности — `403 Forbidden`.


**2. ⚠️ Фильтр задач `?userId=ДРУГОЙ_ID`**

Риелтор передавая чужой `userId` в `/tasks?userId=…` мог видеть задачи коллеги.

→ Исправлено: `tasks.service.list()` теперь бросает `Forbidden` если `isLimitedToOwn && filter.userId !== actor.userId`.


**3. ⚠️ Переназначение чужой задачи через PATCH**

`tasks.service.update()` принимал `input.userId` от риелтора и переназначал task другому сотруднику.

→ Исправлено: при `isLimitedToOwn` запрещено менять `userId` на чужой.


**4. 🔥 SLA-cron возвращал в пул лиды в любой стадии**

T+60 минут после SLA-задачи `clearAssignedUserId` срабатывал даже если лид УЖЕ в `NEGOTIATION` или `SHOWING`. Реальный риск: риелтор работал с клиентом неделю, а ночью SLA забрал ему его лид.

→ Исправлено: `scheduler.service.ts` теперь сбрасывает только если `lead.stage === 'NEW'`. Иначе задача просто закрывается с тегом `[sla:stale_skipped]`.


**5. Mobile: property-form 3 поля схлопывались на iPhone**

`grid grid-cols-3` для Комнат/Этажа/Этажности — на 375px каждое поле получало ~90px и обрезало label.

→ Исправлено: `grid-cols-1 sm:grid-cols-3` — теперь стек на мобильном.

**MEDIUM — ДОКУМЕНТИРОВАНО (фикс в плане недели)**


**6. Property `getById` не проверяет владельца**

Риелтор может открыть `/properties/{UUID}` любого объекта по UUID.

**Статус:** дизайн-решение. Каталог «общий» по умолчанию — фильтр `mine=1` только для UX. Свойств клиента на карточке нет, утечки данных нет.

**Если нужен жёсткий приватный режим** — добавить проверку в `getById(id, currentUserId)` по аналогии с `list()`.


**7. Empty round-robin pool**

Если все агенты `isAvailable=false` (отпуск), лид НЕ попадает в пул через round-robin — assignedUserId остаётся null и лид всё равно появляется в `/pool`, но без notify.

**Статус:** работает корректно, но без уведомления админа. Рекомендация: при `pool.length === 0` создавать notification для всех ADMIN/MANAGER «Все агенты вне работы, лид в пуле».


**8. Property delete не каскадит на ленты**

`schema.prisma`: `interestProperty.onDelete: SetNull` — если удалить property, `lead.interestPropertyId = null`. Лид остаётся, но UI показывает «—».

**Статус:** работает (SetNull правильный выбор), но без визуального предупреждения в UI. Рекомендация: бейдж «Объект удалён» на карточке лида.


**9. Merge clients: частичный fail транзакции**

`clients.service.merge()` использует `$transaction([...])` — при сбое всё откатывается. Но если соединение упало после commit одной части — данные могут разойтись.

**Статус:** уже в транзакции. Дополнительная защита — `try/catch` с rollback-логом. Сейчас приемлемо для самохоста с одной БД.


**10. `Task.create` не обновляет `lead.lastActivityAt`**

Если task создан через API → лид считается «без активности 7+ дней» через неделю, scheduler создаёт дубликат FOLLOWUP-task.

→ **Рекомендация на следующий спринт:** в `tasks.service.create()` после создания делать `await this.prisma.lead.update({ where: { id: leadId }, data: { lastActivityAt: now } })`. 2 строки кода.

**ЛОГИКА — ПРОВЕРЕНО**


✅ **Atomic claim race** — два агента кликают «Взять» одновременно: `updateMany({ where: assignedUserId: null })` — первый выигрывает, второй получает `count=0` и ошибку «уже взяли». Race-safe.

✅ **Property hold** — переход в `NEGOTIATION` блокирует property в `RESERVED`, выход из `NEGOTIATION` без `WON` разблокирует. Транзакция.

✅ **LOST → NEW переход** — `lostReason` и `lostAt` обнуляются автоматически. Чисто.

✅ **Дубликаты телефонов** — `webhooks.controller` использует `upsert by primaryPhone`. Второй inbound от того же `+33…` обновляет существующий клиент, не создаёт второго.

✅ **WON re-engagement** — `scheduler.service` каждые 6 месяцев создаёт FOLLOWUP-task для WON-клиентов. Работает.

✅ **Lead deduplication** — `LeadForm` показывает баннер «У этого клиента уже есть активный лид в стадии X» с deeplink. Защита от случайного дубля.

✅ **Blacklist / Archive client** — `LeadForm` блокирует создание лида с предупреждением. Серверная проверка тоже есть.

**СЦЕНАРИИ «КЛИЕНТ ТЕРЯЕТСЯ» — КОНКРЕТНЫЕ ОТВЕТЫ**


**Сценарий A: Все агенты в отпуске, приходит горячий лид**
→ Round-robin пропускает. Лид в `/pool` с `assignedUserId=null`. Любой агент при возвращении видит его в пуле и берёт. **Не теряется.**

**Сценарий B: Риелтор уволен с 15 активными лидами**
→ `isActive=false` → лиды остаются на нём (нет авто-переноса). **Это потеря.** Рекомендация: в `users.service.deactivate()` сделать `UPDATE Lead SET assignedUserId=NULL WHERE assignedUserId=X` или передать менеджеру.

**Сценарий C: Клиент `WON`, замолчал на 6 месяцев**
→ Scheduler создаёт re-engagement FOLLOWUP-task. Агент видит в `/today`. **Не теряется.**

**Сценарий D: Лид без движения 7+ дней**
→ Бейдж «застрял» на карточке. В `/today` секция «Зависли». **Видно, но без notify.** Можно усилить ежедневной сводкой менеджеру.

**Сценарий E: WhatsApp Lead Ad приходит на номер уже существующего клиента**
→ `upsert by primaryPhone` обновляет email клиента, создаёт новый лид. Если у этого клиента уже есть активный лид — будут ДВА активных лида одного клиента. **Видно второй только при ручном клике**, в воронке оба отрисуются.

→ Рекомендация: при `webhook` проверять `findFirst({clientId, stage: { in: ACTIVE_STAGES } })` и добавлять `Activity` к существующему лиду вместо создания второго.
