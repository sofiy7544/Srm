# Модель сделок и воронок — ТЗ

**Статус:** утверждённое решение (для реализации). Дополняет `CRM_PRODUCT_SPEC.md`.
**Область:** ТОЛЬКО продажа недвижимости. Аренды нет. Стороны: покупатель, продавец,
инвестор, собственник объекта.
**Принцип:** клиент — постоянный центр (хаб); сделка (Opportunity) — временная единица
работы под клиентом. Решение принято в серии бизнес-сессий (см. историю обсуждений).

---

## 1. Когда создаётся Сделка (Opportunity)

**Правило: сделка рождается в момент КВАЛИФИКАЦИИ — не раньше.**

- До квалификации человек — это ранний **лид/контакт** (стадии «Новый / В работе /
  Не дозвонились / Перезвонить»).
- Сделка-оппортьюнити создаётся, когда:
  - **покупатель** — заполнен бриф (бюджет, район, тип, комнаты, цель, срок, оплата); или
  - **продавец** — зафиксированы объект + цена + намерение продать.
- Сделка несёт: ветвь (покупка/продажа), этап, ожидаемую комиссию, дату-прогноз.

**Почему так:** до квалификации это «турист» — в прогнозе комиссии ему не место.
Создание сделки на каждого нового контакта засоряет воронку и ломает прогноз;
создание после показа ослепляет раннюю воронку и не работает для продавца
(у продавца нет «своих» показов). Квалификация — единственная граница, одинаково
работающая для покупки и продажи и дающая честный прогноз. Подтверждено практикой
Salesforce / HubSpot / Pipedrive (opportunity на квалификации) и контакт-центричных
Follow Up Boss / kvCORE.

---

## 2. Клиент vs Сделка

- **Разделяем.** Клиент живёт вечно (годы, несколько транзакций). Сделка временна,
  у неё свой этап/комиссия/объект, она закрывается.
- У человека нет «этапа воронки» — этап есть у его сделки.
- **Один клиент → несколько сделок** (параллельно и во времени):
  - продаёт квартиру И покупает другую (две сделки одновременно — частый кейс);
  - инвестор берёт несколько объектов;
  - вернулся через 3 месяца → **новая сделка** на том же клиенте (старую LOST не реанимируем).
- **Важное различие:**
  - «рассматривает несколько объектов» = **ОДНА** сделка-покупка с шортлистом кандидатов
    (купит один) — НЕ несколько сделок;
  - «покупает квартиру И дом» / инвестор-мультибай / «продаю-чтобы-купить» =
    **НЕСКОЛЬКО** сделок.

---

## 3. Две ветви воронки (после квалификации)

### 3.1 ПОКУПКА (buy-side)
```
Новый → Квалификация → [Подбор ⇄ Показы]×N → Переговоры → Бронь/Документы → Закрыто успешно
                                                                          ↘ Потерян (с причиной)
```

### 3.2 ПРОДАЖА (sell-side)
```
Новый → Квалификация → Оценка+Договор → Листинг → Показы покупателям → Переговоры → Документы → Закрыто успешно
                                                                                              ↘ Потерян (с причиной)
```

Единый вход (Новый → Квалификация), затем расходятся. Тип объекта (квартира/дом/
коммерция/участок) — **фильтр**, не отдельная воронка.

---

## 4. Что НЕ является отдельным этапом (анти-паттерны)

- **«Не подошло»** — это исход показа; цикл возвращает в «Подбор/Показы», не новая стадия.
- **«Просмотр №1/№2/№3»** — один этап «Подбор/Показы» со **счётчиком показов**.
- **«Бронь/задаток»** — **под-статус** внутри «Документы/Сделка», не колонка Kanban.
- **«Пропал/завис»** — **флаг состояния (stale)** поверх текущего этапа, не стадия.

---

## 5. Обязательные правила

- **Квалификация обязательна** перед подбором (нельзя показывать, не зная бюджет/цель).
- **Причина потери обязательна** при переходе в «Потерян» (для ROI источников):
  нет связи / передумал / нашёл сам / выбрал конкурента / недостаточный бюджет / другое.
- **Результат показа** фиксируется структурно: понравился / думает / отказ /
  назначить повторный / начать переговоры — и двигает этап.
- **stale-флаг** + авто-перевод в «Потерян (нет связи)» по тишине N дней.

---

## 6. Сверка с текущей системой (минимум изменений)

Текущие `LeadStage` (NEW→CONTACTED→QUALIFIED→SHOWING→NEGOTIATION→WON/LOST) уже почти
совпадают с **воронкой покупки**. Не взрывать стадии. Нужно:

1. Сделку (Deal) создавать **на квалификации**, а не вручную позже.
2. «SHOWING» трактовать как **цикл со счётчиком показов**, а не одноразовую стадию.
3. Добавить **ветвь продажи** (Оценка+Договор → Листинг) — отдельный набор этапов для
   sell-стороны.
4. «Бронь» — под-статус сделки, не колонка.
5. «stale/завис» — флаг, не стадия.
6. Без аренды — `DealIntent`/UI аренды не развивать в этой итерации.

---

## 7. Итоговая модель движения

```
КЛИЕНТ (телефон + источник, постоянный хаб)
   │ первый контакт
   ▼
КВАЛИФИКАЦИЯ  ◀── здесь рождается СДЕЛКА (Opportunity) с прогнозом комиссии
   ▼
 ┌── покупка ──────────────┐   ┌── продажа ───────────────┐
 │ Подбор ⇄ Показы (цикл)  │   │ Оценка+Договор → Листинг  │
 └────────────┬────────────┘   └────────────┬─────────────┘
              ▼                              ▼
         Переговоры                     Показы → Переговоры
              ▼                              ▼
        Бронь/Документы                 Документы
              ▼                              ▼
       Закрыто успешно   ──или──        Потерян (причина)

(один клиент может держать несколько таких сделок одновременно и во времени)
```

---

## 8. Порядок внедрения (для разработки, отдельными PR)

1. **Квалификация → авто-создание сделки** (граница лид→сделка). Аккуратно на проде:
   не плодить дубли на уже квалифицированных лидах; идемпотентно.
2. **Ветвь продажи** (поля квалификации продавца, этапы Оценка+Договор → Листинг).
3. **Цикл «Подбор/Показы» со счётчиком** + структурный результат показа.
4. **Универсальная карточка `/people/[id]`** (из `CRM_PRODUCT_SPEC.md`) — клиент-хаб
   с несколькими сделками.
5. Поля квалификации (способ оплаты, срок, эксклюзив), stale-флаг, авто-правила задач.

Каждый пункт — отдельный PR с ревью; миграции только аддитивные; без потери прод-данных.
